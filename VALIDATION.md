# Валидация инструментов Куратора
## Цель валидации
Проверить, можно ли доверять автоматической системе проверки эквивалентности (NLI + LLM-judge на базе GigaChat) при массовой генерации мутаций.
Метрика успеха: Cohen's κ ≥ 0.7 (substantial agreement) с ручной разметкой Куратора.
## Данные для валидации
Датасет: data/calibration/manual_mutations.jsonl

Размер выборки: 20 мутаций (по 2 на каждую из первых 10 задач HotpotQA).

Покрытие типов мутаций: paraphrase, reorder, antonym, missing_condition, entity_change.

Разметка: выполнена участником A (Куратор) вручную на основе RUBRIC.md
## Архитектура пайплайна проверки
Для экономии ресурсов используется двухуровневая система:

NLI (MoritzLaurer/DeBERTa-v3-base-mnli): быстрая проверка в оба направления. Если уверенность высокая — вердикт выносится без LLM.

LLM-judge (GigaChat-2-Pro): подключается только для пограничных случаев, когда NLI не уверен (вероятность entailment в диапазоне 0.3–0.7).
## Результаты калибровки
Согласие (Accuracy): 18 из 20 (90.0%)
Cohen's κ: 0.900

Статус: Успешно (κ ≥ 0.7).

## Выводы и ограничения
NLI + GigaChat показали высокую надежность (90% согласия). Система готова к использованию в пайплайне Мутатора.

Слабое место — антонимы (сравнения). GigaChat склонен считать вопросы «Кто старше?» и «Кто младше?» эквивалентными, так как они оба про возраст.
Решение: необходимо добавить в промпт LLM-judge явное правило: «Если мутация меняет направление сравнения (больше/меньше, старше/младше), ответ меняется — мутация НЕ эквивалентна».

Технические сбои. Скрипт должен корректно обрабатывать таймауты GigaChat и делать retry (повторные попытки), чтобы технические ошибки не искажали метрики.
